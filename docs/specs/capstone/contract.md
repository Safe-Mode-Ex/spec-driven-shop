# Контракт — оформление заказа (capstone)

Единственный источник правды о функции оформления заказа. Если в коде появляется поле, метод оплаты или состояние, которого нет здесь, — это либо баг, либо пора обновлять контракт.

## Scope

Оформление заказа: форма доставки с валидацией, выбор способа оплаты, финальный экран подтверждения с итоговой суммой и составом корзины.

Функция строится поверх существующей заглушки в `src/features/checkout/` и не меняет поведение корзины.

## Out-of-scope

- Серверная обработка заказа и отправка на бэкенд. Заказ формируется целиком на клиенте и не покидает сессию.
- История заказов и сохранение заказа в `localStorage`. Снапшот заказа живёт только в памяти на время сессии.
- Реальные платёжные шлюзы и обработка платежей. Выбор способа оплаты — декоративный, с оплатой интерфейс не связывается.
- Ведение расчёта итога. Итог берётся из корзины (`useCart.getTotal()`), в чек-ауте не пересчитывается.
- Маски ввода телефона и автозаполнение адреса через API.
- Разделение доставки на шаги / мультишаговый флоу.

## Constraints

- Структура товаров корзины (`cartItems`) и контракт `onSubmit` не меняются.
- Без новых зависимостей: только React hooks, react-router-dom и существующие утилиты.
- Расчёт итога — строго через `useCart.getTotal()`, чтобы подтверждение и корзина не расходились. Проверка цен в подтверждении — по снапшоту заказа, снятому в момент отправки формы.

## API-эндпоинты

Новых эндпоинтов нет. Функция не делает сетевых запросов: заказ не отправляется на сервер, способ оплаты не обращается к платёжному шлюзу. Существующий API-клиент (`src/api/`) не затрагивается.

## Интерфейсы

### Дорабатываются

- `src/features/checkout/CheckoutPage.jsx` — оркестратор: показывает форму при непустой корзине, переключает на экран подтверждения после отправки, обрабатывает пустую корзину.
- `src/features/checkout/OrderForm.jsx` — форма с адресом и валидацией (существующие поля), плюс встраивается выбор способа оплаты.

### Создаются

- `src/features/checkout/PaymentMethodSelect.jsx` — группировка радиокнопок для выбора способа оплаты. Обязательный выбор, ни один вариант не выбран по умолчанию.
- `src/features/checkout/OrderConfirmation.jsx` — экран подтверждения: состав корзины, итоговая сумма, способ оплаты, контактные данные.
- `src/features/checkout/payment-methods.js` — чистый модуль-перечисление способов оплаты (`PAYMENT_METHODS`), единственный источник допустимых значений.
- `src/utils/order.js` — чистая функция снапшота заказа `buildOrderSnapshot(cartItems, payment, total)`.

### Способ оплаты

Перечисление методов:

| Код | Название в UI |
|---|---|
| `card` | Картой при оформлении |
| `cod` | Наличными при получении |
| `online` | Онлайн-перевод |

Значения `card`, `cod`, `online` — единственные допустимые. `payment.method` снапшота принимает только эти три.

### Формат данных

Снапшот заказа (значение, которое `CheckoutPage` передаёт в `OrderConfirmation`):

```js
{
  contact: {
    name: string,   // валидное имя
    phone: string,  // валидный телефон
    email: string,  // валидный email
    address: string // валидный адрес
  },
  payment: {
    method: 'card' | 'cod' | 'online'
  },
  orderItems: [ // копия состава корзины в момент отправки
    { id, name, price, quantity }
  ],
  total: number // итог из useCart.getTotal() в момент отправки
}
```

`buildOrderSnapshot(cartItems, payment, total)` возвращает `{ orderItems, total }` без контактов и оплаты (те собираются в снапшот в `CheckoutPage`). `total` передаётся готовым значением из `useCart.getTotal()` и не пересчитывается внутри функции. `orderItems` — копии, не ссылки: чтобы состав не менялся, если корзину потом отредактируют. `payment` используется для валидации `payment.method` (одно из `card | cod | online`).

### Валидация (как в `docs/checkout-validation-spec.md`)

| Поле | Правило | Ошибка |
|---|---|---|
| `name` | непустая строка, ≥ 2 символа после trim | «Введите имя» / «Имя слишком короткое» |
| `phone` | `^\+?[0-9]{10,15}$` без пробелов/скобок | «Введите телефон» / «Телефон в формате +7XXXXXXXXXX» |
| `email` | `^[^\s@]+@[^\s@]+\.[^\s@]+$` | «Введите email» / «Некорректный email» |
| `address` | непустая строка, ≥ 5 символов после trim | «Введите адрес доставки» / «Адрес слишком короткий» |
| `payment.method` | одно из `card` \| `cod` \| `online` | «Выберите способ оплаты» |

## Критерии приёмки

1. **Пустая корзина** → страница `/checkout` показывает «Корзина пуста», форма не отображается, `OrderForm` не рендерится.
2. **Пустая форма + submit** → ошибки под всеми полями (включая «Выберите способ оплаты»), `onSubmit` не вызывается.
3. **onBlur после касания** → поле показывает ошибку только после первого касания (touched); на нетронутой форме ошибок нет.
4. **Оплата обязательна** → без выбранного способа кнопка «Оформить заказ» disabled; выбор любого из трёх методов активирует её при валидных остальных полях.
5. **Корректные данные + выбранная оплата** → `onSubmit` вызывается со снапшотом; `CheckoutPage` переключается на экран подтверждения.
6. **Итог не расходится с корзиной** → `total` в подтверждении равен `useCart.getTotal()` на момент отправки; для этого логика расчёта остаётся в корзине и вызывается до снятия снапшота.
7. **Состав корзины в подтверждении** → каждый товар с именем и `price × quantity`; сумма строк соответствует `total` с учётом доставки и скидки по промокоду (сумма выводится как есть, детализация доставки/скидки — опционально).
8. **Доступность** → у полей с ошибкой `aria-invalid="true"` и связь `aria-describedby` с сообщением; сообщения имеют `role="alert"`; радиогруппа оплаты — `<fieldset>` с `<legend>` и семантическими `<input type="radio">`; выбранный метод — `aria-checked`/checked.
9. **Отсутствие сетевых запросов** → оформление заказа не порождает `fetch`; модуль `src/api/` не изменён.
10. **Чистая функция** → `buildOrderSnapshot` покрыта юнит-тестами и не мутирует входные `cartItems`.

## Rollback (секция контракта)

### Уровень 1. Возврат к прежней форме без оплаты и подтверждения

**Когда применять:** баг в новой функции (оплата не выбирается, подтверждение ломается, валидация сломала отправку), быстрое восстановление важнее новых возможностей.

**Как применять:**

1. Выключить новые ветки в `CheckoutPage`: рендерить только `OrderForm` без `PaymentMethodSelect`, оставить прежний экран «Заказ оформлен» вместо `OrderConfirmation`.
2. Собрать и развернуть.
3. Проверить, что форма снова принимает заказ как раньше.

**Ограничение:** пользователь теряет выбор оплаты и детальное подтверждение. Не держать дольше, чем нужно для исправления.

### Уровень 2. Возврат предыдущего релиза

**Когда применять:** функция сломала общий флоу (невозможно оформить заказ из-за регресса корзины/итога), ручное отключение не помогает.

**Как применять:**

1. В CI/CD найти последний зелёный релиз до внедрения функции.
2. Откатиться через пайплайн.
3. Проверить в тестовой среде, что оформление снова работает.
4. Развернуть в продакшен.

### Триггеры отката

- Отправка заказа из формы невозможна (кнопка неактивна при валидных данных, или `onSubmit` не срабатывает) — критичный признак.
- Итог подтверждения расходится с суммой корзины (пользователи видят неверную цену) — критичный признак.
- Массовые жалобы в поддержку на недоступность оформления заказа.

## Что НЕ поддерживается контрактом

- Отправка заказа на сервер и получение его номера.
- Сохранение/восстановление заказа между сессиями.
- Платёжные операции и валидация реквизитов карты.
- Мультишаговая доставка, выбор даты/времени, магазина.
- Промокоды и пересчёт итога в чек-ауте (это ответственность корзины).
