## Высокие (major)

### 1. Сигнатура `buildOrderSnapshot` расходится с контрактом

Контракт фиксирует функцию без `total`:

- `docs/specs/capstone/contract.md:77` — `buildOrderSnapshot(cartItems, contact, payment)` возвращает `{ orderItems, total }`.
- `docs/specs/capstone/architecture.md:25` (A2) — «Функция **не** считает итог — берёт `total` из корзины (`useCart.getTotal()`), чтобы не было второго источника правды».
- `architecture.md:52` — структура файла `buildOrderSnapshot(cartItems, contact, payment)`.

Фактически (`src/utils/order.js:3`):

```js
export function buildOrderSnapshot(cartItems, contact, payment, total) {
  ...
  return { orderItems, total };
}
```

Функция принимает `total` как параметр и возвращает его же. Реализация не «берёт total из
корзины», а просто пробрасывает аргумент. Пока код корректен (`CheckoutPage` передаёт
`getTotal()`), но:

- Сигнатура (и все тесты, и вызов) не соответствуют двум спецификациям.
- `docs/decisions.md` #9 не фиксирует это отклонение — журнал решений не отражает изменение контракта.

**Рекомендация:** либо обновить контракт/architecture/decisions под реальную сигнатуру,
либо привести функцию к документированной. Как минимум — зафиксировать отклонение в
`docs/decisions.md`.

### 2. Параметры `contact` и `payment` не используются по назначению внутри функции

В `buildOrderSnapshot` (`src/utils/order.js`):

- `contact` **не читается нигде** — передаётся в функцию и игнорируется.
- `payment` используется только для валидации `payment.method`, но не попадает в результат.

По замыслу A2 функция должна «из сырых данных корзины, контактов и оплаты делать слепок».
По факту это функция только для `orderItems` (+ проброс `total`), а `contact`/`payment`
являются «мёртвыми» аргументами. Это делает API функции шире её реального поведения и
провоцирует заблуждение у будущего читателя: кажется, что контакты/оплата попадают в снапшот.

**Рекомендация:** либо переработать сигнатуру так, чтобы параметры соответствовали
поведению (например, убрать неиспользуемый `contact`), либо вернуть их в результат согласно
реальному намерению контракта. Сейчас и сигнатура «API», и её документация не отражают код.

### 3. Вторичный источник правды по методам оплаты

`docs/specs/capstone/architecture.md:14` (A1) декларирует: «Перечисление константой —
**единственный источник допустимых значений**, защищает от опечаток в `payment.method`
(проверяется в `buildOrderSnapshot`)».

Но в коде допустимые значения определены в **двух местах**:

- `src/features/checkout/PaymentMethodSelect.jsx:3` — `PAYMENT_METHODS` (`card`,`cod`,`online`).
- `src/utils/order.js:1` — `VALID_PAYMENT_METHODS = ['card', 'cod', 'online']` (продублировано вручную).
- Плюс в `OrderForm.jsx:7` — `PAYMENT_METHOD_VALUES` (производная от `PAYMENT_METHODS`).

Сейчас списки совпадают, но единого источника нет. Если в одном месте добавят метод, а в другом
забудут — ни один существующий тест это не поймает: `OrderForm` и `OrderConfirmation` ходят от
`PAYMENT_METHODS`, а валидация снапшота — от `VALID_PAYMENT_METHODS`. Расхождение пройдёт в продакшен.

**Рекомендация:** сделать `VALID_PAYMENT_METHODS` единственным источником (импортировать его
в `PaymentMethodSelect`, сократив до него же `PAYMENT_METHOD_VALUES`), либо вынести методы в один
экспортируемый модуль-перечисление внутри `src/features/checkout/`+`src/utils/` по решению A1.

## Средние (minor)

### 4. Проверка «не мутирует входной массив» частично бессмысленна

`src/utils/__tests__/order.test.js:48`:

```js
expect(cartItems[0]).toBe(original[0].id === cartItems[0].id ? cartItems[0] : null);
```

Это тавтология: правая часть всегда `cartItems[0]`, когда `original[0].id === cartItems[0].id`
(а ids изначально равны), значит ассерт фактически не проверяет не-мутацию. Напротив тест на
строках 52–57 («создаёт новые объекты, а не ссылки») корректно проверяет это свойство.

**Рекомендация:** убрать строку 48 или заменить на явную глубокую проверку
(например `expect(cartItems.map(i => ({...i}))).toEqual(original)`), оставив осмысленный ассерт
по критерию приёмки 10 («не мутирует входные `cartItems`»).

### 5. `aria-checked` на нативном `<input type="radio">` избыточен

`src/features/checkout/PaymentMethodSelect.jsx:27`:

```jsx
aria-checked={value === method.value}
```

Для нативных `radio` состояние уже раскрывается в дерево доступности через свойство `checked`.
ARIA-авторинг (WAI-ARIA §5.4) не рекомендует дублировать `aria-checked` на нативных контролах —
это лишний, потенциально рассинхронизированный источник состояния. `aria-checked` уместен для
кастомных (без `type="radio"`) элементов; здесь input — нативный.

**Рекомендация:** убрать `aria-checked` (нативный `checked` уже покрывает критерий приёмки 8).

### 6. Правка конфигурационного файла `vitest.config.js` вне границ задачи

В diff добавлена строка в `vitest.config.js`: `exclude: ["tests/e2e/**", "node_modules/**", "dist/**"]`.
AGENTS.md:26 запрещает менять `vitest.config.js` без явного запроса, а risk-register P5 ограничивает
изменения `src/features/checkout/` и `src/utils/order.js`. Намерение здравое (не гонять e2e через vitest,
ведь e2e — отдельный playwright-прогон), но правка конфига выходит за согласованные границы.

**Рекомендация:** согласовать правку конфига явно; на будущее исключать e2e через конфиг тест-раннера
Playwright (он уже изолирован `testDir: './tests/e2e'`), не трогая vitest.

## Отклонённые предложения (deferred / out-of-scope)

  ответственности корзины, чтобы не плодить второй источник расчёта (decisions.md #11).
- **D3. Добавить маску ввода телефона и автозаполнение адреса.** **Отклонено:** явное
